Any column with a custom renderer ([`renderer`](/docs/next/columns#renderers-and-editors) — DOM, React, or
imperative React) can choose what its cells show while the grid is actively scrolling. There are two choices:
**text** and **live**.

<Callout title='Why this exists' type='info'>
	Mounting or re-rendering every custom cell on every scroll frame is the biggest cost in a virtualized grid with rich cells. `scroll` lets you
	decide per column how much of that work to do mid-scroll.
</Callout>

## `text` and `live`

Set the choice with `scroll` under the renderer's `capabilities`:

| `scroll` | What cells entering view show during scroll                                                                             | Default for     |
| -------- | ----------------------------------------------------------------------------------------------------------------------- | --------------- |
| `text`   | Stand-in text. Renderers already mounted stay as they are. The real renderer mounts once scrolling settles.             | React renderers |
| `live`   | The real renderer, mounted or updated during scroll within the per-frame budget. Never blank (see below for the limit). | DOM renderers   |

Columns with no custom renderer draw plain text and need no setting.

```typescript
{
	field: 'status',
	header: 'Status',
	renderer: {
		kind: 'react',
		component: StatusBadge,
		capabilities: { scroll: 'live' },
	},
}
```

## `text` — stand-in text during scroll

With `text`, a cell that scrolls into view shows plain text instead of mounting the component. When scrolling stops,
the real renderer mounts. Cells that were already drawn before the scroll started keep their renderer.

The text is the cell's formatted value. To show something different, give the column a `scrollText` function. It
receives the raw and formatted value and returns a plain string:

```typescript
{
	field: 'severity',
	header: 'Severity',
	renderer: {
		kind: 'react',
		component: SeverityBadge,
		capabilities: {
			scroll: 'text',
			scrollText: ({ value, formattedValue }) => `● ${formattedValue || String(value)}`,
		},
	},
}
```

`scrollText` returns a string only — no JSX or DOM. Use it for a short label that reads well in a hurry.

## `live` — the real renderer during scroll

Use `live` when the component itself must be visible while scrolling: bars, badges, avatars, or anything where
text would look wrong.

DOM renderers are `live` by default. A DOM renderer's `update()` is a direct DOM write with no React involved, so it
is cheap enough to run inside the scroll frame. A cell that scrolls into view calls your renderer's `update()` with
its new row, or `mount()` the first time a slot uses it. Cells that stay in view are not touched.

```typescript
const SparklineRenderer = {
	mount(container: HTMLElement, params: { value: unknown }) {
		const bar = document.createElement('div');
		container.appendChild(bar);
		const paint = (value: unknown) => {
			bar.style.width = `${Number(value) || 0}%`;
		};
		paint(params.value);
		return { update: (next: { value: unknown }) => paint(next.value) };
	},
};

// No capabilities needed: DOM renderers are 'live' by default.
const column = { field: 'trend', header: 'Trend', renderer: { kind: 'dom', renderer: SparklineRenderer } };
```

React renderers are `text` by default. Set `scroll: 'live'` to mount and update them during scroll too. In the
bench (100,000 rows, 10 React columns, real wheel input) this draws every visible cell correctly on every frame
for about 28% more main-thread time than `text`.

### The per-frame budget

Live work is budgeted so a fast scroll cannot starve the frame. A cell the budget cannot reach in time shows its
stand-in text for that frame (never blank, never another row's content) and is completed right after.

## `scrollState` — reacting to scrolling

Renderers receive `isScrolling` and `phase`, but by default a change to those alone does not update or re-render
the cell. A renderer is updated only when its value, row, column, or editing, focus or selection state changes,
so scroll start and scroll end cost nothing for most renderers.

A renderer that draws differently while scrolling opts in with `scrollState`:

```typescript
{
	field: 'status',
	header: 'Status',
	renderer: {
		kind: 'react',
		component: StatusBadge,
		capabilities: { scrollState: true },
	},
}
```

Without `scrollState`, the `isScrolling` and `phase` a renderer receives reflect its last update, not the live
scroll state.

## Imperative renderers for high-frequency cells

For cells that change many times per second, such as a ticking price, even a React state update per tick is
too much. Declare the column as `kind: 'imperativeReact'`. The grid then calls `ref.current.update()` directly on a
`forwardRef` component that exposes [`ImperativeCellHandle`](/docs/next/grid-api), bypassing React's scheduler.

```tsx
const LivePrice = React.forwardRef<ImperativeCellHandle<Row>, CellRendererProps<Row, number>>((props, ref) => {
	const spanRef = React.useRef<HTMLSpanElement>(null);
	React.useImperativeHandle(ref, () => ({
		update(next) {
			if (spanRef.current) spanRef.current.textContent = next.formattedValue || String(next.value);
		},
	}));
	return <span ref={spanRef}>{props.formattedValue || props.value}</span>;
});

const column = { field: 'price', header: 'Price', renderer: { kind: 'imperativeReact', component: LivePrice } };
```

Use this only where ordinary updates show dropped frames under your real data volume: your component owns its DOM
updates. The [Realtime Dashboard example](/docs/next/examples) shows all three strategies side by side — an
imperative React "Change %" column, a DOM "Price" column, and a plain React "Volume" column.

## Grid-level budgets

`rendererOptions.live` on `<Grid>` sets the shared per-frame budget for every `live` cell. It is grid-wide because
it limits total work across all visible cells:

```tsx
<Grid
	rows={rows}
	columns={columns}
	getRowId={(row) => row.id}
	rendererOptions={{
		live: { maxMsPerFrame: 4, maxMountsPerFrame: 12, maxUpdatesPerFrame: 40, rowOverscan: 2, columnOverscan: 1 },
	}}
/>
```

| Option               | Default   | Effect                                                                                      |
| -------------------- | --------- | ------------------------------------------------------------------------------------------- |
| `maxMsPerFrame`      | `4`       | Milliseconds of DOM renderer work per frame.                                                |
| `maxMountsPerFrame`  | unlimited | New React renderers mounted per frame.                                                      |
| `maxUpdatesPerFrame` | unlimited | Updates to already-mounted React renderers per frame.                                       |
| `rowOverscan`        | `0`       | Extra rows beyond the viewport that are prepared for live work, so they are ready on entry. |
| `columnOverscan`     | `0`       | Extra columns beyond the viewport that are prepared for live work.                          |

<Callout title='Tune this before you need to' type='warn'>
	React `live` cells are unlimited by default. If a dashboard with many `live` columns drops frames under heavy scroll, cap `maxMountsPerFrame` and
	`maxUpdatesPerFrame`. A cell over the cap shows its stand-in text for that frame and is completed right after.
</Callout>

## The rendering window

The grid renders the rows and columns in view plus a margin around them (overscan), so a scroll step lands on
cells that are already drawn. Four `<Grid>` props size that margin:

| Prop               | Default | Effect                                                                                                     |
| ------------------ | ------- | ---------------------------------------------------------------------------------------------------------- |
| `rowOverscanPx`    | `400`   | Pixels of rows rendered above and below the viewport.                                                      |
| `colBuffer`        | `2`     | Columns rendered left and right of the viewport.                                                           |
| `overscanAdaptive` | `false` | Grows the margin on the side the grid is scrolling toward, in proportion to scroll speed.                  |
| `runtimeLimits`    | —       | Hard caps on rendered rows and cells (`maxRenderedRows`, default 500; `maxRenderedCells`, default 20,000). |

```tsx
import { Grid } from '@eregister/wit-grid-react';

type Row = { id: string; value: number };

export function FastScrollingGrid({ rows }: { rows: Row[] }) {
	return (
		<Grid
			rows={rows}
			columns={[{ field: 'value', header: 'Value' }]}
			getRowId={(row) => row.id}
			rowOverscanPx={200}
			overscanAdaptive
			runtimeLimits={{ maxRenderedRows: 60, maxRenderedCells: 2_000 }}
		/>
	);
}
```

Scroll from user input is drawn in the same frame it happens. A scroll set from script — `scrollTop` assigned inside
`requestAnimationFrame`, a scroll animation, an auto-scroll — is drawn one frame later, so each step must land inside
the margin. If a scripted scroll moves further per frame than `rowOverscanPx`, turn on `overscanAdaptive`, which
extends the leading edge while the grid is moving and shrinks it again once it stops. It is off by default because it
renders more rows and cells during fast scrolls.

When `runtimeLimits` bind, the overscan gives way first: rows and columns in view are always kept, and only the
margin shrinks.

## Choosing

- Nothing custom on the cell → no setting needed.
- DOM renderer → leave the default (`live`): cells are drawn in place during scroll.
- React renderer, stand-in text is fine mid-scroll → leave the default (`text`), and add `scrollText` if the
  formatted value is not the best label.
- React renderer whose component must show while scrolling → `scroll: 'live'`.
- Data changes many times per second and a React update per tick drops frames → `kind: 'imperativeReact'`.
